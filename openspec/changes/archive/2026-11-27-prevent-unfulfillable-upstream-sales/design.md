# Design

## Context

见 proposal.md。现有同步、下单、支付和采购路径分别处理状态，库存充足和查询失败均可能放行。生产使用 SQLite/PostgreSQL 通用事务；HTTP 请求不得在事务内发出。

## Goals / Non-Goals

**Goals:** 共用可售核验和停售能力，保留现有计价、库存字段、请求节流和队列。

**Non-Goals:** 不增加数据库字段或依赖，不改真实生产数据，不部署；不引入跨站锁库存、预采购或自动退款。

## Decisions

- 每轮完整分页，不再依赖无法证明有效的增量过滤。完整快照缺失触发详情查询，已停售且持续缺失无需重复查询。
- 商品详情 404 归为不可售；product_not_found 不代表确认删除。暂态错误与畸形响应阻止购买，不能当商品删除。
- Mapping 提供批量可售核验与采购失效回写窄端口。实时核验仅更新库存/可售状态，不调用整套改价同步。
- 复用并扩展现有事务装配，所有停售写入绑定同一事务，按字段更新，统一先锁商品映射再写规格；远端查询在事务外。
- 下单、支付各自核验，预览仅用本地状态。同轮按商品合并详情请求，按上游规格汇总数量。恢复旧支付链接、渠道接口及本站易支付中转均复用付款核验。
- 自动停售不关闭映射；本地商品/规格保持停售直到人工复售，库存为零的补货可自然解除售罄。
- 商品/SKU 数据落库共用状态处理；分类树、价格解析失败不能阻断停售。

## Risks / Trade-offs

- 严格核验增加请求与等待 → 共用详情、已有节流、有限 GET 重试和明确期限。
- 首次缺失积压增加同步耗时 → 已停售商品不重复详情查询，任务防重与连接总期限。
- 已发出的支付二维码及核验到采购的状态变化窗口 → 正常记录实际收款与采购失败，及时告警停售，沿用售后。
- 历史 disabled/deleted 映射无法区分人工停用 → 保留，不批量启用；后续单独审核。

## Migration Plan

本地完成测试和审核后再申请部署；生产数据与历史异常订单需部署后另行复核。回滚代码不自动上架任何商品，不更改已收款事实。
